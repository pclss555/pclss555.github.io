抖音 SSL Unpinning 实战：3 个 Hook 点的完整拆解

目标：让 Reqable（MITM 代理）能解密抖音 39.9.0 的 HTTPS 流量。
平台：Android 16 arm64，Frida + 抖音 com.ss.android.ugc.aweme。
结论先行：证书校验全部藏在 native 层的两个 BoringSSL 库。

一、背景：为什么常规方案全部失效

抖音的网络栈不走 OkHttp，而是 TTNet 定制的 Cronet。证书校验（SSL Pinning）全部在 native 层完成，分布在两个 so 里：

库 角色 关键特点 Hook 思路
libsscronet.so 主 API 流量 静态编译 BoringSSL，零 SSL_* 导出，无法按符号 hook IDA 定位偏移，attach 固定偏移
libttboringssl.so TTNet 通用网络库 SSL_* 函数直接导出 按导出符号 hook

两个库用的是 BoringSSL 的 custom_verify 机制：

二、核心思路

找到每个 custom_verify 回调入口 → Interceptor.attach → onLeave 里 retval.replace(0)。

三、3 个 Hook 点详解

Hook 点 1：libsscronet.so + 0x2BEB90（TCP 链路验证回调）

  • 是什么：cronet 内部 TCP TLS 链路的 custom_verify 回调入口（39.9.0 arm64 偏移）。
  • 怎么找：so 无任何 SSL 导出，只能 IDA 打开 → 定位静态符号 SSL_CTX_set_custom_verify → 查交叉引用，调用处第三参数（回调指针）就是回调地址。
  • 怎么 hook：
  • 效果：主 API 流量（h2 over TCP）的证书校验被放行，这是抓包成功的核心点。

Hook 点 2 & 3：libttboringssl.so 的 SSL_CTX_set_custom_verify / SSL_set_custom_verify

  • 是什么：TTNet 通用库的回调注册函数（有导出符号）。回调地址不是固定的，而是在注册的瞬间作为第三参数传进来。
  • 怎么 hook：attach setter 本身，onEnter 时截获第三参数拿到回调地址，再对回调做同样的 retval 覆盖：
  • 效果：不管 app 用哪个 API 注册校验，注册瞬间回调就被 pin 住，版本更新一般不需要改脚本。
  • 细节：如果回调函数太小导致 attach 失败，用 fallback——构造一个新回调替换 args[2]，新回调先调用原回调（保留副作用）再返回 0。注意 NativeCallback 要放进全局池防 GC。
